How the System Is Built

A technical reference for anyone maintaining, extending, or auditing the system.

System Overview

Archaív is composed of two independent, cooperating software processes running on the same Raspberry Pi:

  • The main web application - a Flask app that staff and members interact with through a browser, handling borrowing/returning, account management, reporting, and the alarm's software-side state.
  • The Pi controller - a separate headless process that talks directly to the fixed UHF RFID Reader Antenna, the HF/NFC Reader/Writer, and the GPIO-driven alarm relay.

The two processes communicate over a small set of authenticated HTTP endpoints protected by a shared secret key (RFID_LISTENER_KEY), so RFID/alarm hardware logic stays fully separated from the transaction-management logic, while the main app remains the single source of truth for classification and alarm state.

Backend Stack

Implemented primarily in Python 3, using Flask as the web framework and Jinja2 for server-side templating. In production the app is served through Waitress (a pure-Python WSGI server) rather than Flask's own dev server, for stability under continuous, unattended, multi-day operation.

Data is stored in SQLite with Write-Ahead Logging enabled, so reads aren't blocked while a write is in progress - relevant given the mix of frequent RFID-detection writes and simultaneous staff browser use. The database can optionally be encrypted at rest via SQLCipher (AES-256).

Because deriving the SQLCipher encryption key is comparatively expensive per connection, the app maintains a small pool of already-unlocked connections, one per active thread, instead of opening a fresh connection per request.

Scheduled/background tasks (automatic backups, expired-session cleanup, overdue-member sweeps, maintenance-due notifications) run inside the same application process via APScheduler.

Frontend Stack

The interface uses HTMX to update sections of a page directly from the server without a full reload, paired with vanilla JavaScript for interactive behavior (live-updating tables, keyboard shortcuts, modals) and Chart.js for the Reports and Monitoring Trends visualizations. Styling is Tailwind CSS. This combination was chosen for its low resource footprint on Raspberry Pi-class hardware, avoiding a full single-page-app framework's overhead while still feeling responsive.

Hardware-Software Interface

On the Pi controller side, several hardware interfaces work together:

  • The gpiozero library (via its lgpio pin-factory backend) drives the GPIO-connected relay module that energizes the alarm.
  • pyscard (PC/SC standard) communicates with the ACS ACR122U HF/NFC Reader/Writer for Master Key Card verification.
  • The fixed S4A UHF-202406 antenna communicates over Ethernet using its own RCP command protocol, rather than USB keyboard-emulation mode, which proved unreliable for continuous, unattended reading during development.
  • The Pi controller reports every detection and card tap to the main app over HTTP via the Python requests library; shared configuration (including the authentication key) is managed through python-dotenv environment files.

Alarm Circuit

The alarm relay is wired to Raspberry Pi GPIO 18 (BCM numbering) through an intermediate 2N2222 NPN transistor stage, rather than driving the relay module's trigger input directly:

  1. GPIO 18's 3.3V logic-level output switches the transistor.
  2. The transistor supplies the 5V signal the relay module's trigger side actually requires.
  3. The relay closes on its isolated, higher-current output side to switch the 12V Warning Lamp with Buzzer.

This both steps the Pi's 3.3V signal up to the voltage the relay expects, and keeps the Pi's GPIO circuitry electrically isolated from the relay's own switching current.

Verified on real hardware Because the relay itself holds no state of its own, its behavior after a restart depends entirely on a background polling loop that reconciles it against the app's current alarm state. This was verified by triggering a live alarm, rebooting the Pi mid-alarm, and confirming the relay re-energized automatically on restart, then correctly cleared on a real Master Key Card tap.

Security

Several layers protect the system independently of one another:

  • Staff passwords are hashed, never stored in plaintext; every state-changing action is gated by role-based access control.
  • CSRF tokens are required on state-changing requests.
  • Machine-to-machine endpoints used by the Pi controller authenticate with a separate shared secret key (not a staff login) and are rate-limited.
  • The database can optionally be encrypted at rest via SQLCipher (AES-256); independently, file permissions on the database and config file are restricted to the app's own account.
  • Behind a reverse proxy, the deployment configures trusted proxy hops so the rate limiter and audit log attribute requests to the real client, not the proxy's own address.
  • RFID tag identifiers are escaped before rendering on the Monitoring page, preventing a crafted tag value from executing as script content.
  • Disabling the alarm feature in System Settings immediately clears any active alarm, rather than leaving it stuck and unreachable through normal deactivation.

Deployment & Network

The system's deployment and network infrastructure combines several elements:

  • Both processes run as persistent Linux systemd services, starting on boot and restarting automatically on failure.
  • The web app sits behind Caddy, a reverse proxy that terminates HTTPS using a locally generated, self-signed certificate authority, so staff never see an unencrypted login page.
  • The Pi is reached via its mDNS hostname (resolved through avahi) rather than a fixed IP, so it stays reachable even if its network address changes.
  • Caddy compresses HTML/CSS/JS responses in transit (gzip/zstd), and the compiled CSS/JS are separately minified - both reducing data transferred to a staff member's browser.
  • The Pi controller's systemd service starts after the main app's - a soft ordering hint, not a hard dependency, closing a brief startup-race window.

Response-Time Data Collection

The system captures three millisecond-precision timestamps for every RFID detection event: the instant the antenna reports the tag, the instant the main app finishes processing it, and (for alarm-triggering events) the instant the relay is actually energized. A dedicated Monitoring Trends view presents this as summary statistics, a per-event time-series chart, a raw event log, and a CSV export.

Data Flow: An Unauthorized Event, Start to Finish

  1. A tagged tool passes the fixed UHF antenna at the monitored exit.
  2. The Pi controller's background listener detects the tag and POSTs it to the main app's /api/v1/rfid-events endpoint (authenticated via the shared secret key).
  3. The main app looks up the tag against assets. If the matching asset has no active borrowing record, the event is classified unauthorized and recorded in rfid_events.
  4. The app's response tells the Pi controller to activate the alarm; the Pi controller calls gpiozero to energize the relay immediately.
  5. A background polling loop on the Pi controller separately re-checks the app's alarm status every few seconds, so a software-side dismissal (or a reboot mid-alarm) still keeps the physical relay in sync with the app's actual state.
  6. An Admin taps the Master Key Card at the HF/NFC reader; the Pi controller POSTs this to /api/v1/rfid-events/deactivate, the app clears the active alarm, and the Pi controller de-energizes the relay.
