Backups

The running main app backs up the database automatically every 30 minutes via an internal scheduled job - no separate configuration needed. An Admin can also trigger a manual backup from System Settings.

An optional second, independent backup path exists as a systemd timer (toolroom-backup.timer / .service) for cases like writing to a mounted USB drive on a schedule, or wanting backups to continue even during a stretch where the main app is deliberately stopped. Most deployments don't need this on top of the built-in scheduler.

Provisioning RFID Tags

Tag/card writing is not a feature inside the app. Instead, use RFIDDemo.exe, a free standalone program run directly on the workstation, together with the USB UHF RFID Reader/Writer:

  1. Open RFIDDemo.exe on the workstation and connect to the reader/writer.
  2. Present the new tag/card and write its identification data using RFIDDemo's own interface.
  3. Copy the tag/card's ID into the app - either by scanning it into the RFID Tag ID field on the asset's Add/Edit form, or the member's record.

This keeps tag writing decoupled from the browser entirely, so it works the same regardless of HTTPS or browser support.

Updating the App

  1. Pull/copy the updated source onto the Pi.
  2. If any template added new Tailwind utility classes, rebuild static/css/output.css: ./tools/tailwindcss.exe -i static/css/input.css -o static/css/output.css --minify.
  3. If static/js/ui.js changed, regenerate the minified bundle with terser (see the comment above the script tag in templates/base.html for the exact command).
  4. Restart the service: sudo systemctl restart toolroom. Database migrations in migrations/ apply automatically on this restart - nothing else to run by hand.

FAQ

Does the system need internet access to work?
No. Every asset the app needs (CSS, JS, fonts) is self-hosted, and the Pi is reached via mDNS on the local network - the whole system works with the router's internet uplink completely disconnected.

What happens to the alarm if the Pi loses power mid-alarm?
The relay itself holds no state. On restart, the Pi controller's polling loop reads the app's current alarm status within a few seconds and drives the relay to match - so an active, undismissed alarm correctly comes back on after a reboot, and a cleared one correctly stays off.

Can the system tell if a tool is entering or leaving the room?
No - it uses a single monitored RFID point, which reports detection only, not direction of travel. The alarm decision is based on the tool's transaction status at the time of detection, not movement direction.

Why two separate .env files?
The main app and the Pi controller are separate, independently-runnable processes - the Pi controller has its own config (hardware pins, reader settings) that the main app has no reason to know about, and vice versa.
